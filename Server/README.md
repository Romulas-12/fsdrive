# FSDrive Server

Сервер синхронізації `fsdrived`, спільний для всіх клієнтів, і те, що потрібно клієнтам від нього:
бібліотеки `FSDriveCore` (протокол, типи API, хешування, закріплення ключа сервера) і
`FSDriveClientKit` (мережевий клієнт), а також CLI-клієнт `fsdrive`. Пакування під конкретні NAS — у
`Packaging/<система>` (`qnap`, `synology`; інші додаються поруч). Архітектура: [../docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md).

Усі команди нижче виконуються з цієї теки (`Server/`).

## Збірка

Потрібні Xcode / Swift 6 і macOS 14+.

```bash
swift build -c release
```

Бінарники: `.build/release/fsdrived` і `.build/release/fsdrive`.

## Сервер на QNAP (QPKG)

```bash
scripts/build-qpkg.sh          # -> build/qpkg/FSDrive_<версія>_arm_64.qpkg  (--x86 додає x86_64)
```

Скрипт збирає статичний Linux-бінарник у контейнері Swift (`scripts/build-linux.sh`, потрібен Docker/OrbStack
лише на Mac для збирання) і пакує його офіційним QNAP QDK.

Встановлення:

1. App Center → «Встановити вручну» → `FSDrive_<версія>_arm_64.qpkg`. Пакет не підписаний QNAP, тому в
   налаштуваннях App Center треба дозволити застосунки без цифрового підпису.
2. Відкрийте **FSDrive** у головному меню QTS (розділ «Застосунки») і виберіть:
   - **де зберігати файли**: у домашніх теках (`<домашня тека>/FSDrive`) або в окремій спільній теці, де для
     кожного користувача створюється тека за іменем або за ID;
   - **хто може користуватися FSDrive** — позначте користувачів QTS і натисніть «Зберегти».
3. На Mac у застосунку FSDrive введіть адресу сервера та ім'я й пароль QTS. Пароль перевіряє QTS; FSDrive
   зберігає лише токен цього пристрою (його можна відкликати на сторінці налаштувань).

Як поводяться теки користувачів:

- Наявна тека (`fsdrive` у домашній теці чи тека користувача в спільній) підхоплюється з усім вмістом.
- Файли, які записує FSDrive, належать користувачу, група — `administrators`, права `0660`/`0770`: доступ має
  автор і адміністратори, інші користувачі — ні. Наявні файли FSDrive не перепризначає.
- Поруч лежить прихована `.fsdrive-system` (версії, кошик, незавершені завантаження) — на тому ж томі, що
  й файли, тож версії не копіюються.
- Якщо обліковий запис видалили й створили знову з тим самим іменем, FSDrive не віддасть йому стару теку,
  доки адміністратор не натисне «Прив'язати теку».
- Зміна режиму сховища дає користувачу нове місце; пристрої під'єднуються до нього й доносять свої файли.

Сервіс слухає порт 8740, працює з пониженим пріоритетом (`nice`), лог — у `fsdrived.log` в теці застосунку.
Інша тека для даних: `setcfg FSDrive DataRoot /share/<тека> -f /etc/config/qpkg.conf`, потім перезапуск.

## Сервер на Synology (SPK)

```bash
scripts/build-spk.sh           # -> build/spk/FSDrive_<версія>_x86_64.spk  (--arm додає armv8 для ARM64-моделей)
```

Той самий Linux-бінарник (`scripts/build-linux.sh`), запакований у звичайний tar-архів SPK; набір інструментів
Synology не потрібен. Потрібен DSM 7.

Встановлення:

1. Package Center → «Встановити вручну» → `FSDrive_<версія>_x86_64.spk`. Пакет не підписаний Synology, тож DSM
   попередить про невідомого видавця.
2. Одноразове налаштування від root. DSM 7 запускає сторонні пакети від окремого користувача без прав root, а
   `fsdrived` має записувати файли від імені кожного користувача й перевіряти паролі в DSM. Тому пакет лише
   вмикає й вимикає службу, а запускає `fsdrived` невелика служба systemd (`bin/fsdrive-supervise`), яку
   ставить `bin/fsdrive-root.sh`. Сторінка FSDrive у DSM показує обидва способи:
   - **Планувальник завдань** (зберігається після оновлень DSM): Control Panel → Task Scheduler → Create →
     Triggered Task → User-defined script, користувач `root`, подія Boot-up, команда
     `/var/packages/FSDrive/target/bin/fsdrive-root.sh`; потім «Run»;
   - або один раз через SSH: `sudo /var/packages/FSDrive/target/bin/fsdrive-root.sh`.
3. Далі все як на QNAP: у FSDrive (головне меню DSM) виберіть, де зберігати файли (домашні теки — потрібна
   служба домашніх тек у Control Panel → User & Group → Advanced — або спільна тека) і кому дати доступ.

Що інакше, ніж на QNAP:

- Пароль перевіряє DSM через свій API входу на цьому NAS (`SYNO.API.Auth`, пароль передається curl через
  stdin), тож діють правила DSM: вимкнені облікові записи, застарілі паролі, привілеї застосунків. Із
  двоетапною перевіркою DSM вхід поки не працює.
- Користувачі — локальні облікові записи DSM з UID від 1024 (без `guest` і службових користувачів пакетів).
- Файли належать користувачу з групою `administrators` (gid 101).
- Дані сервера — у `/var/packages/FSDrive/var/data`, лог — `/var/packages/FSDrive/var/fsdrived.log`, порт
  8740 (інший: число у `/var/packages/FSDrive/var/port`). Брандмауер DSM знає службу як «FSDrive».
- Сторінка налаштувань працює від користувача пакета й відповідає лише адміністраторам DSM (сесія й
  SynoToken перевіряє `authenticate.cgi`). Токен сервера для неї кладе root-служба у `var/cgi`.
- Після видалення пакета root-служба за хвилину вимикає й видаляє себе сама. Завдання в Планувальнику
  треба видалити вручну.

## Репозиторій пакетів

Замість ручного встановлення NAS може брати FSDrive й оновлення з репозиторію пакетів. Для кожної системи
NAS це окремий GitHub-репозиторій `Romulas-12/fsdrive-packages-<система>` зі статичним сайтом на GitHub Pages:
там лише зібрані пакети, код лишається тут.

| Система | Репозиторій | Адреса для магазину застосунків |
|---|---|---|
| QNAP | [fsdrive-packages-qnap](https://github.com/Romulas-12/fsdrive-packages-qnap) | `https://romulas-12.github.io/fsdrive-packages-qnap/repo.xml` |
| Synology | [fsdrive-packages-synology](https://github.com/Romulas-12/fsdrive-packages-synology) | `https://romulas-12.github.io/fsdrive-packages-synology/x86_64.json` (Intel/AMD), `…/armv8.json` (ARM) |

```bash
scripts/build-qpkg.sh --x86
scripts/publish-repo.sh qnap     # збирає сайт у build/repo/qnap і публікує одним комітом
```

Кожна публікація замінює історію одним комітом, тож старі пакети не накопичуються. Той самий сайт для
іншого хостингу: `scripts/build-repo.py qnap --base-url https://<хост>/<шлях>`. Спільний опис застосунку
лежить у `Packaging/repo/app.json`. Нова система — це функція `build_<система>` і запис у `SYSTEMS`
у `scripts/build-repo.py`, тека `Packaging/<система>` і новий репозиторій `fsdrive-packages-<система>`.

Synology: `scripts/build-spk.sh --arm`, потім `scripts/publish-repo.sh synology`. DSM 7 питає джерело пакетів
звичайним GET (модель, архітектура й збірка DSM — у параметрах адреси), тож статичного сайту досить; але
відповісти по-різному для різних процесорів він не може, тому для кожної архітектури своя адреса
(`x86_64.json`, `armv8.json`). У Package Center → Settings → General → Trust Level треба вибрати «Any publisher».

На QNAP: App Center → Налаштування → «Репозиторій застосунків» → «Додати», адреса з таблиці. Пакет не
підписаний, тож дозвіл на застосунки без цифрового підпису потрібен і тут.

Якщо FSDrive раніше ставили вручну, App Center відмовляється ставити його з репозиторію («Failed to find the
application on the cloud server»): `qpkgd` пов'язує встановлений пакет із репозиторієм полем `store` у
`qpkg.conf`, де лежить MD5 адреси репозиторію. Прив'язати наявне встановлення (налаштування й файли
лишаються), потім натиснути «Install»:

```bash
setcfg FSDrive store $(printf %s 'https://romulas-12.github.io/fsdrive-packages-qnap/repo.xml' | md5sum | cut -c1-32) -f /etc/config/qpkg.conf
```

Інсталятор порівнює `<platformID>` з моделлю NAS цілком, тому `repo.xml` містить окремий `<platform>` для
кожної моделі ARM64 (ARM-моделі QTS називає однаково `TS-NASARM`, і 32-, і 64-бітні).

## Сервер на Mac

```bash
.build/release/fsdrived init --root ~/FSDriveData
.build/release/fsdrived serve --root ~/FSDriveData --host 0.0.0.0 --port 8740
```

`init` друкує токен доступу. Файли бібліотек лежать у `~/FSDriveData/files/<користувач>/<бібліотека>/`,
службові дані — у `~/FSDriveData/.system/` (база, попередні версії, кошик).

Наявну теку можна підключити як бібліотеку без переміщення файлів (має бути на тому ж томі):

```bash
.build/release/fsdrived import --root ~/FSDriveData --name Фото --path ~/FSDriveData/files/me/Фото
```

Зміни, зроблені у Finder прямо на сервері, підхоплюються скануванням (при старті й кожні 10 хв,
або `POST /v1/libs/{id}/scan`).

> Сервер працює лише по TLS 1.3, і в локальній мережі теж. Сертифікат він створює сам при першому
> запуску (`.system/tls`), тож центр сертифікації не потрібен. Клієнти запам'ятовують ключ сервера
> при першому з'єднанні (як SSH) і далі приймають лише його. Короткий код ключа показують застосунок
> на Mac і сторінка FSDrive у QTS, щоб їх можна було звірити. Інший ключ (підміна сервера або нова
> інсталяція) клієнт відхиляє; щоб прийняти справжній новий ключ, треба вийти й увійти знову.

## Клієнт командного рядка

```bash
.build/release/fsdrive login https://сервер:8740 ТОКЕН --device MacBook   # --pin sha256/… замість довіри першому
.build/release/fsdrive create Документи
.build/release/fsdrive sync Документи ~/Документи-FSDrive --watch 30
```

## Швидкість

Виміряно між MacBook (Wi-Fi 6, 160 МГц) і TS-435XeU (2,5 GbE, NVMe RAID1), файл 1 ГБ:

| | Один TCP-потік (сирий) | FSDrive |
|---|---|---|
| Mac → NAS | 10 МБ/с | ~100 МБ/с |
| NAS → Mac | 173 МБ/с | ~165 МБ/с |

Вивантаження з Mac по Wi-Fi обмежене приблизно 10 МБ/с на одне TCP-з'єднання, тому клієнт шле до 32 частин
паралельно, а великі файли завантажує 8 потоками. NAS при цьому: ~60% одного ядра з чотирьох, ~55 МБ пам'яті.
Клієнт під час вивантаження займає ~300 МБ (буфери URLSession) — це відоме обмеження.

## Тести

```bash
swift test
scripts/e2e.sh /tmp/fsdrive-e2e          # синхронізація, версії, конфлікти
scripts/e2e-users.sh /tmp/fsdrive-users  # користувачі QNAP, режими сховища, права, ізоляція
scripts/test-repo.py                     # сайт пакетів QNAP: repo.xml так, як його читає App Center
scripts/check-repo.py https://romulas-12.github.io/fsdrive-packages-qnap   # опублікований сайт
```

`test-repo.py` збирає сайт із підставних пакетів і перевіряє, що інсталятор QNAP знайде правильний пакет
для моделей ARM64 і x86 (і не дасть ARM64-збірку 32-бітним ARM), що всі посилання ведуть у сайт, а
`release.json` збігається з файлами. `publish-repo.sh` запускає його перед публікацією, а після неї чекає,
доки GitHub Pages віддасть новий `repo.xml`, і запускає `check-repo.py`: усі посилання відповідають, а
розмір і SHA-256 пакетів збігаються з `release.json`.

`e2e.sh` піднімає сервер і два «пристрої» та перевіряє: початкову синхронізацію, дельта-передачу,
збереження версій, перейменування, видалення, зміни на сервері через Finder, конфлікти й порожні теки.

## Що не входить у 0.1

Кілька користувачів, веб-інтерфейс, FSEvents/inotify (поки що періодичне сканування), E2EE,
очищення старих версій, `sendfile()` для віддачі файлів.
